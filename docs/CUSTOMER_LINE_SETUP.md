# Customer line setup

> Historical provider-submission flow for internal operators. New Customer accounts use the separate portal on `my.blucom.ir`, cannot submit providers/numbers, and are documented in [CUSTOMER_TENANCY.md](CUSTOMER_TENANCY.md). Internal panel permissions are documented in [SINGLE_PANEL_RBAC.md](SINGLE_PANEL_RBAC.md).

The customer portal at `hub.blucom.ir` now follows this flow:

1. Connect one or more customer-owned SIP providers. The customer enters a provider name, connection label, server, and either account credentials or an IP-based connection method. New gateways belong to the customer's tenant and remain disabled with `verification_status=pending`.
2. Add a customer-owned phone number and select one of those tenant-owned providers. The number is normalized to E.164, globally unique, and remains `pending` until reviewed. There is no number catalog or purchase option in this flow.
3. Optionally choose a weekly time condition with Jalali closure dates, then choose an existing phone user or create one for open hours. Closed hours can route to a tenant-owned phone, team, or published menu; play an uploaded announcement and hang up; or disconnect immediately. Without a schedule, the existing single-answerer behavior applies. In Quick Wizard mode, outbound caller ID is selected explicitly in the final step. Outside Quick Wizard mode, a new phone without an outbound route gets this number as its outbound route. The phone password is displayed only after creation or regeneration.
4. Configure a softphone or desk phone using the server, port, username, and one-time password. The portal does not claim to know live registration state.

Admins review customer-owned gateways and numbers at `/admin/customer-connections`. Approval requires separate provider and number checks. Customer routes cannot execute while the number or gateway is pending. Admin-managed legacy gateways have no tenant owner and retain their existing behavior.

Customers can correct and resubmit pending or rejected provider and number details. Provider passwords must be re-entered during resubmission; the old value is never shown. Editing an approved provider or assigned number through the onboarding form is disallowed. A rejected provider or number can be corrected without losing the related answerer setup.

## FreeSWITCH behavior

The XML-CURL directory can return enabled users from active tenants. Extension numbers remain globally unique because FreeSWITCH's current internal profile uses one directory domain. Authenticated local calls are limited to the caller's tenant; the existing Blucom transfer path remains available for its working DID. Customer inbound routes bridge directly to the tenant's selected phone user. Outbound XML requires an enabled, approved gateway and an assigned number owned by the same tenant and linked to that gateway.

Customer provider credentials are encrypted in the database and are never displayed in the portal or logs. New gateway names are generated by the server. Customer input cannot become an arbitrary FreeSWITCH bridge target.

## Inbound time conditions

The optional schedule is stored on each inbound route. The portal accepts Persian or Western digits and displays Jalali closure dates; the database stores exceptional dates as Gregorian `YYYY-MM-DD`. Weekly intervals are half-open (`start` inclusive, `end` exclusive) in the configured IANA time zone, currently presented as `Asia/Tehran`. Closure dates override weekly hours. FreeSWITCH asks XML-CURL for the `public` dialplan on each call; Laravel selects the current open or closed action from database state. No `reloadxml`, SIP profile change, or FreeSWITCH restart is needed for a schedule edit.

Announcement uploads are converted with FFmpeg to a private, FreeSWITCH-readable 16 kHz mono WAV on the existing `ivr` disk. The portal serves the stored audio only to an authorized customer of the owning tenant. A missing announcement or disabled/foreign destination produces no matching inbound route; it never falls through to outbound dialing. An IVR already playing remains authorized across a schedule boundary for that call.

Deployment requires `ffmpeg` on the Laravel host and shared read access to `storage/app/ivr` from FreeSWITCH, as with existing IVR prompts. The code returns a validation error when FFmpeg cannot start. The migration `2026_09_29_000008_add_schedule_to_inbound_routes` is additive and must run after the preceding call history, queue, and IVR migrations.

## Operational activation

The deployment currently has `VOIP_GATEWAY_XML_ENABLED=false`. Consequently, approving a customer gateway in Laravel does not by itself load that gateway into Sofia. Customer inbound and outbound XML routes remain gated while this flag is false, even after admin approval. The FreeSWITCH gateway XML-CURL binding and profile rescan procedure must be validated on the server before customer gateways can make live provider calls. Do not represent admin approval as live registration. Existing `provider-trunk` and Sofia profiles remain unchanged by this feature.

Read-only check on 2026-09-25: `mod_xml_curl` is loaded, and the existing `provider-trunk` reports `REGED` / `UP`. The XML-CURL configuration has `blucom-directory` and `example` bindings but no gateway binding. No FreeSWITCH configuration was changed.

For a controlled activation, inspect and back up the current external profile, enable the gateway XML-CURL binding, verify a harmless lookup, then rescan the external profile and inspect gateway status. Test one inbound and one outbound call with the customer and provider before declaring the line operational. Ordinary number, answerer, and phone changes use XML-CURL and do not require XML file edits or a FreeSWITCH restart.
